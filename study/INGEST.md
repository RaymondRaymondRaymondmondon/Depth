# INGEST.md: how Claude Code builds a course pack

This is the procedure for turning a class's materials into a course pack the Study can serve (Master Reference,
"The Study: course packs" and "The Study: how Claude Code learns a course"). Follow it step by step, every time a
course is added or updated. Nothing Claude Code reads persists between sessions except what is on disk: **if a fact
is not in the pack, it is not known; go back to the sources.**

Everything here stays on the player's machine. `study/courses/`, `study/reports/` and the class materials are
gitignored and are never sent over the network (the Live Tutor, when switched on, receives only one item, its unit's
skill list and the player's answer).

---

## 0. Every session starts the same way

1. Read `pack/STATUS.md`, `pack/conventions.json`, and every open report in `study/reports/` for this course.
2. **Reports first.** Before any new work, resolve every open report: re-run the gates on the reported item, fix it
   or retire it (quarantine with a reason), note the outcome in `study/CHANGELOG.md` (a line with `error:` if the
   report revealed a real error), and set the report's `status: resolved`. When a report reveals a real error,
   search the whole pack for the same mistake (the same wrong fact, the same template bug) and fix every instance.
3. Pick **one unit** (or one large textbook chapter). A session reads, builds and verifies one unit, then stops.
   Quality never trades against finishing a course in one go.
4. End every session by updating `pack/STATUS.md` (per unit: which phase is done, what is in progress, open
   conflicts, open reports).

## Folder layout

```
study/
  INGEST.md          this file
  CHANGELOG.md       one line per pack build: course, version, item count (and "error:" lines for errors found)
  reports/           the player's error reports (one file each; "status: open" until resolved)
  courses/<ID>/
    source/          everything the player drops in, untouched (syllabus/ lectures/ textbook/ problem_sets/
                     exams/ notes/ anki/). Big PDFs may be hard links to the player's own copies.
    work/            rendered page images and OCR text (tools/pdfpages.ps1); scratch, never cited directly
    pack/
      course.json        id, code, title, term, version, type, sources (id, rank, file or url, pages or
                         sections), exams, units in order (id, title, type, status, sections)
      conventions.json   notation, simplified-answer rules, calculators, the instructor's phrasing, "forbid" list
      objectives.json    every learning objective with its page id and units
      coverage.md        every source page: used / out_of_scope (reason) / unreadable (what was tried) / queued (unit)
      conflicts.md       disagreements between sources, "- [ ]" open, "- [x]" settled by the player
      review_queue.md    quarantined items waiting for the player (or instructor/TA) to settle
      STATUS.md          per-unit progress
      units/Uxx.json     the skill graph for the unit
      knowledge/Uxx.json the knowledge cards
      anchors/Uxx.json   the player's own problems, profiled
      blueprints/Uxx.json the skill x tier grid
      items/Uxx.json     the bank (items + templates)
      instances/Uxx.json template instances, generated by --course-expand (never hand-written)
      quarantine/Uxx.json items pulled from rotation, each with its reason
      verify/Uxx.gates.json  the recorded results of the sub-agent gates (blind solve, grounding, adversarial)
      verify/Uxx.log     written by --course-verify
```

## The tools

| Command | What it does |
|---|---|
| `tools\pdfpages.ps1 -Pdf <f> -From a -To b -Out <dir> -Ocr` | Renders PDF pages to PNG (and OCR text) with Windows' own engines. `-Count` prints the page count. |
| `depth.exe --course-verify [course] [unit]` | Structure, coverage, skill graph, blueprint, and gates 1, 2 (comparison), 3 (citations + verdict), 4 (verdict), 5, 6. Writes `verify/Uxx.log`. Exit 0 only with zero errors. |
| `depth.exe --course-report [course]` | Per unit: sources read / out of scope, cards, skills, objectives, items per tier and label, quarantine and why, open conflicts, open reports, verified error rate. |
| `depth.exe --course-expand [course] [unit]` | Expands each template into verified instances (`count`, default 200). Every instance passes gate 1 or is dropped; a template with any failing instance must be repaired. |
| `depth.exe --course-seed-test` | The seeded-error fixture (`study/courses/_seeded_test`): 20 planted errors, all must be caught, no good item rejected. |
| `depth.exe --expr-test` | The expression engine's own fixture. |

## 1. Inventory

List every file in `source/` and classify it: syllabus, schedule, lecture, textbook chapter, problem set, exam,
answer key, notes, or Anki export. Record it in `course.json` `sources` with:

- a short **source id** (`SYL`, `ACT1`, `NOTES2`, `AC2`, `OSC2`, `STW9`...), used in every page id;
- its **rank** (below);
- `file` (relative to the course folder) and `pages` (the page count, from `pdfpages.ps1 -Count`), or `url` and
  `sections` for a web textbook.

### Source authority

| Rank | Source | Used for |
|---|---|---|
| 1 | Instructor materials: slides, lecture notes, instructor keys, syllabus, study guides, announcements | Scope, emphasis, conventions, definitions as the course states them |
| 2 | The assigned textbook(s) | Depth, derivations, worked examples, practice problems |
| 3 | The player's own notes and Anki decks | What the player finds hard, their phrasing, gaps |
| 4 | Other textbooks the player adds | Extra problems and alternative explanations, **never conventions** |
| 5 | Claude Code's general knowledge | Checking and explaining only; anything it contributes is labelled "beyond course materials" |

When two sources disagree, the higher rank wins for conventions and emphasis, and the conflict is logged in
`conflicts.md`. A mathematical or physical fact is not subject to ranking: if a key has an arithmetic error, the
recomputed answer is correct, and the discrepancy is logged for the player.

## 2. Read every source (in chunks)

The goal: every page of relevant material read, understood and indexed; nothing skimmed.

- **Extraction.** Render every page with `tools\pdfpages.ps1 -Ocr` into `work/`. OCR text is only a finding aid:
  **every page is also looked at as an image**, because equations, figures and tables are garbled or dropped by
  extraction (OCR drops most mathematics). Scanned pages go through OCR and are then checked against the image.
- **Web textbooks.** Fetch each assigned section; note its examples, activities and exercise prompts. Page ids are
  section-level (`AC2/5.4`, `AC2/5.4/ex5.4.3`).
- **Equations.** Transcribe each equation you use into the pack's plain math syntax (the one `expr` parses), then
  re-read it against the page image. A transcription that does not match is fixed before anything uses it.
- **Figures.** Diagrams get a structured description in the card that uses them: what is shown, labels, arrows,
  and what the figure teaches.
- **Page ids.** `SRC/pNNNN` for PDFs (the PDF's own page index, 4 digits), `SRC/section[/anchor]` for web texts.
  All citations use these ids.
- **Chunks.** Long textbooks are read a section at a time; cards are written to disk as each section is finished.
- **Coverage log.** `pack/coverage.md` lists every source page, one per line (ranges allowed):
  `- OSC2/p0301-p0335 | used | 3.1 Integration by Parts ... 3.4 Partial Fractions`
  `- STW9/p0001-p0470 | out_of_scope | Calc I material; not on the syllabus`
  `- NOTES2/p0001-p0016 | queued | U02, read when U02 is built`
  `- SCAN/p0007 | unreadable | OCR and 2x render tried; photo is out of focus`
  A page missing from the log fails `--course-verify`. `queued` pages belong to units not built yet; they cannot be
  cited until read and changed to `used`.

## 3. Scope and emphasis

- **Objectives.** Every learning objective in the syllabus, study guides and lecture outlines goes in
  `objectives.json` with its page id and the units it belongs to.
- **Emphasis weights.** Each unit (and heavy topic) gets a weight from lecture time, slides, and practice and exam
  problems: `course.json` `units[].weight`. Weights set how often a topic appears in Mixed review and Exam
  simulation, and raise its blueprint counts.
- **Conventions.** `conventions.json`: notation, variable names, how logs and absolute values are written, whether
  `+ C` is required, what counts as simplified, exact vs decimal answers, calculators, the instructor's phrasing of key
  definitions, and a `forbid` list of text that breaks the conventions (with the reason). Every item follows it.
- **Out of scope.** Textbook sections not on the syllabus are `enrichment`: never in Exam simulation, only in
  practice if the player turns enrichment on.

## 4. The knowledge base

Write atomic cards to `knowledge/Uxx.json`: one idea per card, small enough to test on its own.

```json
{ "id": "U01.K3", "type": "procedure", "title": "Choosing u (LIATE as a guide)",
  "text": "...", "pages": ["ACT1/p0014", "AC2/5.4"], "outside": false }
```

Types: `definition`, `principle`, `procedure`, `worked_example`, `structure_function`, `lesion_deficit`,
`comparison`, `misconception` (the wrong belief, why it is tempting, the correction). Every card carries at least one
page id. A card that cannot be cited is dropped or marked `"outside": true` with a `note`; outside cards are never the
only basis for an item's correct answer. Conceptual courses favour mechanism, prediction and comparison cards.

## 5. The skill graph

`units/Uxx.json`: skills, each **one testable ability phrased as a verb** ("choose u and dv", "set up the partial
fraction form for repeated linear factors"). If a skill needs two separate things to go right, split it.

```json
{ "id": "U01.S2", "name": "choose u and dv for integration by parts", "cards": ["U01.K3"],
  "prereqs": ["U01.S1"], "objectives": ["LT1"], "misconceptions": ["U01.M2"] }
```

Misconceptions come from the player's graded work, errors flagged in keys and textbooks, common-error notes in the
sources, and Claude Code's knowledge of typical mistakes (labelled as such, `outside`). Prerequisites may name skills
of earlier units or earlier courses (`COURSE:SKILL`). The graph must pass (checked by `--course-verify`):
every objective maps to a skill and every skill to an objective; every skill cites a card and every card belongs to a
skill; prerequisites have no cycles; no skill is too broad to isolate in one problem.

## 6. Anchors: the player's own problems

Every practice problem, problem set, quiz and exam problem goes in `anchors/Uxx.json`:

```json
{ "id": "U01.A4", "source": "ACT1/p0007", "prompt": "...", "answer": "...", "skills": ["U01.S2"],
  "steps": 3, "form": "expr", "cue": 1, "repr": "equation", "keyMatch": true, "conflict": "" }
```

- **Profile:** skills, step count, answer form, whether the method is cued (`cue` 0 none, 1 cued, 2 named), the kind
  of numbers, the representation.
- **Independent solve:** solve every anchor before looking at its key, then compare. A mismatch is investigated; if
  the key is wrong, record `keyMatch: false`, the working in `conflict`, and an open line in `conflicts.md`.
- **Unit profile:** the median and range of steps across the unit's anchors (computed by the verifier). The tier
  rules measure against it.
- **The player's mistakes:** graded work links each lost point to its skill and misconception; those skills are
  weighted up in Weak spots.
- Anchors also enter the bank as items labelled `coursework` ("From your coursework"), with hints and solutions.

## 7. Type each unit

`computable` (checked automatically and exactly: numeric tolerance, units, symbolic equivalence), `conceptual`
(closed forms automatic; short answers by keyword rubric; long answers self-graded or by the Live Tutor), or
`mixed` (per item).

## 8. The blueprint

Before writing items, write `blueprints/Uxx.json`: a grid of skills x tiers with a target count per cell.

- every skill at Easy and at Medium at least twice each;
- Hard covers every skill at least once, each with a named twist;
- Challenging items together cover every skill, each combining at least three skills;
- emphasis weights raise the counts for heavy topics;
- at least 10 shipped items per tier (40 per unit), plus templates for computable units.

## 9. Author the bank

`items/Uxx.json` holds `items` and `templates`. Every item:

- **Is built from cards.** It lists its `skills` and `cards`; its answer follows from those cards alone.
- **Has one right answer or a clear rubric.** Free response carries a rubric of specific points, each tied to a card.
- **Follows `conventions.json`** so problems feel like the instructor's.
- **Uses realistic values** (physics and chemistry: plausible numbers, sensible answer sizes; no calculators here,
  so exact answers).
- **Has meaningful distractors.** Every wrong choice comes from a listed misconception card and has its own `why`.
- **Is new, not copied.** Items differ from anchors and textbook problems in setup, not only in numbers.
- **Carries its metadata:** `tier`, `form` (`expr`, `numeric`, `choice`, `multi`, `parts`, `text`), `steps`,
  `cue`, `novelty` (0-2), `twist` (Hard), `sources` (page ids), `label` (`computed`, `sourced`, `coursework`),
  `status` (`shipped`, `quarantined` + `reason`).
- **Carries its checks** (computable items; gate 1 runs them): `check` entries of type `antiderivative` (`of`),
  `definite` (`integrand`, `a`, `b`, bounds may be `inf`), `diverges` (`integrand`, `a`, `b`, `at`), `equal`
  (`expr`), `value` (`expr`), `ode` (`rhs` in x and y, optional `at`/`y0`), `euler` (`rhs`, `x0`, `y0`, `h`, `n`),
  `series` (`term`, `n0`), `derivative` (`of`: the answer is its derivative), `integral` (the answer is an integrand; `a`, `b`, `value`: its integral must equal a value found another way, for set-up-only items), `arclength` (`of`: the answer is the arc-length integrand √(1 + f′²) of that curve, possibly simplified), `solves` (`expr`, `var`: the numeric answer, put in for `var`, makes `expr` zero). Solution steps may carry `math: {lhs, rhs, upToC}`, checked as identities.
- **Carries known wrong answers** (`wrong`: answer + the named `mistake`) so feedback names the mistake.

Tiers, measured against the anchor profile:

| Tier | Rule |
|---|---|
| Easy | one skill, fewer steps than the anchor median, friendly numbers, the method named or strongly cued (`cue` >= 1) |
| Medium | the anchors' skills, step count (within their range) and answer form |
| Hard | an anchor plus one twist (extra step, unfamiliar setup, earlier-unit skill, word problem, the integral returns...), method not cued, at least the median steps |
| Challenging | three or more skills, multi-part (`form: parts`), no cueing; needs command of the whole unit |

**Templates** (computable units): variables with ranges (`from`/`to`, `choose`, `nonzero`), `derived` values,
`constraints` (`a != b`, `integer: expr`, `>`...), and an `item` whose text uses `{a}`, `{a:p}` (parenthesised if
negative), `{a:c}` (as a coefficient: 1 -> "", -1 -> "-"), `{a:s}` (a signed term " + 3" / " - 3"). The answer is a
formula in the variables; `--course-expand` fills in 200+ instances and verifies each one a second way (gate 1).
The game never needs anything but the stored instances.

## 10. Hints and solutions

- **Hint 1, a nudge:** which idea or skill applies. It never gives away the answer.
- **Hint 2, the setup:** the first step, done.
- **Hint 3, nearly there:** every step but the last.
- **Worked solution:** every step shown, each naming its `skill` and citing its `card`, with a one-line `why` for any
  step that is not obvious. It ends with the `commonMistake` for this problem type and the page(s) to `reread`.

## 11. The six gates

Every item passes six gates in order. Gates are run by **separate passes** (sub-agents) so no pass checks its own
work. Failing any gate sends the item back for repair or into quarantine.

| Gate | What | How |
|---|---|---|
| 1 Computation | the answer and every intermediate step are right | `--course-verify` recomputes each item a second way (differentiate an antiderivative, integrate numerically, sum partial sums, plug a solution into its ODE), checks every `math` step, and proves every listed wrong answer and every distractor really is wrong |
| 2 Blind solve | the problem as written leads to the keyed answer | a sub-agent sees **only the prompt** (and choices), solves it, and writes its answers to `verify/Uxx.gates.json` `blind`; `--course-verify` compares them with the key (symbolically for expressions, up to a constant for antiderivatives) |
| 3 Grounding | every claim is supported by the player's sources | automatic: every item, card and step citation resolves to a `used` page in `coverage.md`, no answer rests only on outside cards; plus a sub-agent that lists each claim with its supporting excerpt and page id (`grounding` verdict) |
| 4 Adversarial | it cannot be misread or answered another way | **two independent** sub-agents try to break it (neither sees the other's verdict): a second defensible answer, ambiguity, a missing assumption, an impossible value, a leaky hint, an arguably right distractor, content outside scope; the item passes only if both pass it (`merge_gates.ps1 -Adversarial a.json,b.json`) |
| 5 Consistency | it agrees with the rest of the pack | automatic: conventions (`forbid`, `+ C`), no hint 1/2 states the answer, no duplicate or copied prompts; the adversarial pass also compares it with other items and cards on the same skills |
| 6 Tier audit | it meets its tier's rule | automatic, against the anchor profile |

Gate 1 applies to computable items. Conceptual items skip it but must pass gate 3 with an excerpt for the keyed
answer and every distractor's explanation.

The gates file:

```json
{ "blind":       { "U01.E01": "x sin(x) + cos(x) + C", "U01.C01": ["...", "..."] },
  "grounding":   { "U01.E01": { "ok": true, "note": "" } },
  "adversarial": { "U01.E01": { "ok": true, "note": "" } } }
```

A blind solver that finds a problem ambiguous still answers it but adds a note; `--course-verify` then fails the item until the third pass (below) records a ruling in `adjudicated` (`merge_gates.ps1 -Adjudicated r.json`, `{ "adjudicated": { "<id>": { "ok": true|false, "note": "..." } } }`).

Why two reviewers and the note rule: the seeded-error test (2026-09-30) showed one adversarial reviewer passing an arguably-correct distractor that another caught, and a blind solver noticing an ambiguous stem that no gate acted on.

Sub-agent briefs: the blind solver receives only item ids, prompts and choices (never keys, hints, solutions or
metadata). The grounding pass receives the item and the cards and source excerpts, never the author's reasoning. The
adversarial reviewer receives the full item and the unit's other items, and is told its job is to break them.

### When checks disagree

1. If the blind solve disagrees with the key, or the blind solver flags the problem as ambiguous, a **third pass** solves it with full access to the sources and both
   answers, and explains which is right and why.
2. If it confirms the key and finds the wording ambiguous, the wording is fixed and the item goes back through
   **every** gate.
3. If the disagreement cannot be resolved with certainty, the item is quarantined (`status: quarantined`, a
   `reason`, or moved to `quarantine/Uxx.json`) and listed in `review_queue.md` for the player (or their instructor
   or TA) to settle.
4. A quarantined item is never shown. Better fewer items than one wrong one.

### Confidence labels

| Label | Meaning |
|---|---|
| Computed | passed all six gates, and the answer was recomputed symbolically or numerically |
| Sourced | passed all six gates, and every claim is backed by an excerpt from the player's materials |
| From your coursework | an anchor, re-solved and matching its key (or with the key's error logged) |
| Player-checked | the player approved it in Review mode (added to its other label) |

## 12. Write and log

1. `depth.exe --course-expand <course> <unit>` (computable units), then `depth.exe --course-verify <course> <unit>`
   until it reports zero errors. Fix or quarantine every failing item; never ship around a failure.
2. `depth.exe --course-report <course>`: zero unresolved gate failures among shipped items.
3. Set the unit's `status` to `built` in `course.json`, bump `version`, update `STATUS.md`.
4. Add a line to `study/CHANGELOG.md`: `YYYY-MM-DD <course> v<version> <unit>: items <shipped total> (...)`.

## The player's review pass and the error-report loop

- **Review mode** (Courses drawer) shows about 10 items per new unit, riskiest first (items that needed
  adjudication, Challenging items, long solutions, skills with few sources). The player marks each good, unclear or
  wrong; unclear or wrong goes straight to quarantine with the player's note. A reviewed unit is marked as such.
- **Report a problem** on every problem card: wrong answer, unclear wording, typo, out of scope, other, plus a note.
  The item leaves rotation immediately and the report is written to `study/reports/`. If the player's answer was
  marked wrong and they report the key, that attempt doesn't count against mastery until resolved. Reports are
  resolved first thing next session (step 0). The pack's error history stays, so the verified error rate per course
  is visible in `--course-report`.

## Keeping a course current

- **New lectures or problem sets:** drop them in `source/`, find the units they touch, read them, add cards and
  items, re-run the gates only for affected items. Progress on unchanged items is kept.
- **Returned exams and graded work:** the most valuable sources. They become anchors; lost points map to skills and
  misconceptions; recheck the tier calibration against how the real exam compared with the Medium profile.
- **Instructor corrections:** into `source/` at rank 1; every affected item is re-checked.
- **Calibration from use:** items whose first-try accuracy falls outside their tier band (about 85 / 65 / 45 / 25%),
  or that the player often reports unclear, are rewritten or re-tiered next session.

## New semesters

Make a new folder under `study/courses/`, drop the materials into `source/`, and run this file on it. Finished
terms move to the Past Terms shelf and stay usable. Skills from finished courses stay in the combined graph, so a new
course can list them as prerequisites (`COURSE:SKILL`).
